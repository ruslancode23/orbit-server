# AGENTS.md — orbit-server

Инструкции для AI-агентов (Claude Code, Codex, Cursor и др.) и для людей.

Orbit — открытое приложение с постоянными голосовыми комнатами для команд и сообществ.
Этот репозиторий — API-сервер. Web-клиент — отдельный репозиторий `orbit-web`.
Источник требований — PRD 3.1 (Orbit — PRD 3.0 в Claude Docs). Текущий этап — spike: голос и экран в браузере.

## Команды

```bash
cp .env.example .env
make up           # PostgreSQL (localhost:5433), SeaweedFS (S3), LiveKit в Docker
make migrate
make run          # API на :8080
make check        # golangci-lint + go test -race — запускай перед тем, как считать задачу готовой
make fmt          # gofumpt + goimports
make api          # после изменения api/openapi.yaml
make sqlc         # после изменения db/queries или миграций
make migrate-new name=create_users
make help         # все цели
```

Инструменты (sqlc, goose, golangci-lint) закреплены в `tools/go.mod` и вызываются через `go tool`.
Не ставь их глобально и не добавляй в основной `go.mod`.

## Стек (PRD 11.2)

Go 1.26, `net/http` + chi, OpenAPI + oapi-codegen (strict server) с валидацией kin-openapi,
`coder/websocket`, PostgreSQL через pgx + sqlc, миграции goose, slog,
LiveKit (SFU) для голоса и экрана, S3 (SeaweedFS локально, ADR-0003). Позже: river для фоновых задач.

Не добавляй: ORM (gorm, ent), Redis, брокеры сообщений, микросервисы, logrus/zap, testify/mock-фреймворки
без необходимости. Решение уровня стека фиксируй в `docs/adr/`.

## Структура — модульный монолит

```
cmd/orbit/            сборка зависимостей, запуск, graceful shutdown — без бизнес-логики
internal/config/      конфиг только из переменных окружения
internal/api/         сгенерировано из api/openapi.yaml (make api), не править
internal/platform/    инфраструктура: httpserver, postgres, logger
internal/<module>/    доменные модули: auth, servers, messages, voice, files, moderation
migrations/           SQL-миграции goose (только вперёд; Down обязателен)
db/queries/           SQL для sqlc → internal/platform/postgres/db (сгенерированный код не правь руками)
```

- Модуль владеет своими таблицами. Другой модуль обращается к ним через Go-интерфейс модуля, а не SQL.
- Зависимости передаются явно через конструкторы (`NewHandler(db)`), без глобального состояния и `init()`.
- Интерфейсы объявляет потребитель, а не реализация (`health.Pinger`).

## Обязательные правила

- **Права проверяются на сервере** в каждом обработчике и каждой подписке на события. Скрытая кнопка на
  клиенте — не защита. Изоляция данных между серверами (workspace) покрывается тестами.
- Секреты — только из переменных окружения. Новая переменная → `internal/config` + `.env.example` + README.
- Пароли — argon2id (`internal/auth`). Сессии — непрозрачные токены: клиенту уходит токен, в БД лежит только его
  SHA-256. Токен живёт в cookie `orbit_session` (HttpOnly, SameSite=Lax, Secure вне разработки) — её же браузер
  пришлёт при апгрейде WebSocket, чего заголовком не сделать. `auth.Middleware` кладёт сессию в контекст и никого
  не отклоняет; хендлер без сессии отвечает 401 сам, вне генерируемых хендлеров — `auth.RequireSession`.
- Не доверяй `X-Forwarded-For` без списка доверенных прокси (`chi/middleware.RealIP` не используем): адрес
  клиента — только `clientip.From(ctx)`, список — `ORBIT_TRUSTED_PROXIES`. Лимиты по адресу и по имени
  входа — `ratelimit.AllowKey`/`Check` (см. README, «Лимиты входа и регистрации»).
- SQL только параметризованный, через sqlc.
- Вложения (`internal/files`): загрузка идёт через сервер, тип определяется по содержимому
  (`http.DetectContentType`), html/svg/js не принимаем; скачивание — подписанной ссылкой из
  объектного хранилища (`internal/platform/objectstore`), не через сервер.
- Права на сервере — только через роли: `servers.Service.Require(ctx, ws, user, perms.X)` или права в канале
  (`channels.Service.Permissions`, `View.Permissions`). Не проверяй `role == admin`: роль `admin` в API
  выводится из права `administrator` и нужна только старым клиентам. Скрытый канал — `ErrNotFound`, не
  `ErrForbidden`. Правила расчёта и иерархия — `internal/perms`, README «Роли и права».
- Новый `events.Kind` без публикатора не пройдёт `TestEveryKindHasAPublisher`; новое событие добавь и в
  `SERVER_EVENTS` web-теста `event-coverage.test.ts`, иначе клиент может его не обработать.
- Живые события — через `internal/events` (шина в процессе) и `internal/gateway` (WebSocket,
  `/api/v1/ws`, вне OpenAPI). Модуль публикует событие через свой узкий интерфейс и не знает о
  подписчиках; права проверяются при каждой подписке, а бан и кик закрывают поток сразу
  (`Hub.Revoke`). Медленный клиент отключается с кодом `behind` и догоняет историю по курсору.

## Код

- Ошибки оборачивай с контекстом: `fmt.Errorf("create server: %w", err)`. Сравнение — `errors.Is/As`.
- Первый аргумент функций с I/O — `ctx context.Context`. HTTP-клиенты и запросы — с контекстом.
- Логи — `slog` со структурными полями, без `fmt.Println`. Не логируй токены, пароли, тела сообщений.
- API описывается в `api/openapi.yaml` до кода: правишь спецификацию → `make api` → реализуешь метод
  `api.StrictServerInterface` в своём модуле. Не пиши роуты и JSON-декодирование вручную, не правь `*.gen.go`.
- Ошибки — в едином формате `{"error":{"code","message"}}` (`httpx`, схема `Error`). Валидация входа описывается
  в схеме; в домене остаются только правила, которые схема выразить не может.

## Секретные чаты (SCRUM-82)

`internal/secrets` владеет устройствами, их публичными ключами, one-time pre-keys, привязкой
«чат ↔ устройства» и конвертами. Приватные ключи и открытый текст не покидают устройство и не должны
появляться на сервере нигде: ни в БД, ни в логах, ни в метриках.

- ADR — `docs/adr/0005-secret-chats-olm.md`, модель угроз и чек-лист ревью —
  `docs/threat-model-secret-chats.md`.
- Секретный чат — пара устройств (`channels.kind = 'secret'`, `secret_chat_devices`). Обычные
  эндпоинты сообщений и прочитанного отвергают такой канал 404: `messages.Send/History/Since` и
  `reads.Mark/Channel` проверяют вид канала. Не добавляй секретному каналу текстовую историю.
- One-time key выдаётся один раз: `ClaimOneTimeKey` — `DELETE … RETURNING`. Не делай список ключей
  доступным, не логируй `body` конверта и не расширяй метаданные (отправитель, получатель, размер, TTL).
- `expires_at` у конверта и вложения обязателен; TTL не больше 7 дней (`MaxEnvelopeTTL`,
  `maxSecretFileTTL`). Просроченные конверты убирает `secrets.Sweeper`, файлы — `files.Sweeper`.
  Подтверждение получателя удаляет конверт сразу.
- Личные события (беседы, сообщения в них, `secret.envelope`) идут через `events.Hub.SubscribeUser` /
  `PublishToUser` и кадр `resume`; не публикуй их в поток сервера.
- Регистрация устройства проверяет подпись ed25519 над `orbit-device-v1|<userId>|<identityKey>|<signingKey>`.
  Права проверяются на сервере: `X-Orbit-Device` должен принадлежать вызывающему, получатель конверта —
  быть собеседником чата.
- Тесты: `internal/secrets/service_test.go` (подпись, лимиты, одноразовые ключи, TTL, чужое
  устройство), `internal/gateway` (личный поток и докат по курсорам).

## Онлайн-статус (SCRUM-96)

`internal/presence` владеет тем, кто в сети: соединения WebSocket (по одному на вкладку), выбранный
аккаунтом статус и то, что из этого видят другие.

- Наружу уходит только `MemoryStore.Status`: он уже применил выбор аккаунта. «Невидимка» обязана
  превратиться в `offline` везде — в `GET /workspaces/{id}/members` и в `presence.updated`, — иначе
  приватность течёт. Не публикуй `Availability` и не считай статус в хендлере сам.
- Публикует только `Service` (`flush` из `Run`): дебаунс 5 с на аккаунт и грейс 30 с на `offline`
  живут там. Хендлеры и гейтвей только сообщают о соединении и кадрах — без событий напрямую.
- Аудитория — серверы аккаунта (`Hub.Publish`) и друзья (`Hub.PublishToUser`). Посторонний не
  должен узнать ничего: тест `TestStrangerSeesNothing`. Тот же круг знакомства определяет видимость
  «общих» списков (`GET /users/{userId}/mutual`): они открыты только тому, кто видит профиль.
- Состояние в памяти процесса, как voice-presence: перезапуск восстанавливается переподключениями,
  а выбор статуса клиент присылает кадром `status` заново. Хранилище для нескольких инстансов
  подставляется через `PresenceStore`.
- Тесты: `internal/presence` (статусы, дебаунс, грейс, невидимка, посторонний) и
  `internal/gateway` (кадры `presence`/`status`, Connect/Disconnect).

## Друзья (SCRUM-98)

`internal/friends` владеет таблицей `friendships`: одна строка на пару (`user_low < user_high`),
`status` — `pending` или `accepted`, `requested_by` — автор заявки.

- Заявка отправляется точным ником без учёта регистра. Ответ на `POST /friends/requests` всегда
  один и тот же `202` с `{"message":…}`: сохранённая заявка, несуществующий ник, запрет политики,
  блок и гость неотличимы. Не добавляй в этот ответ ни флаг, ни код, ни разное тело.
- Встречная заявка сразу принимается: строка меняет `status` на месте, поэтому у пары не может
  появиться вторая строка. Принятие проверяет лимит друзей (409), отклонение и отмена — только
  свою сторону; списки всегда берутся из сессии.
- Политика `users.friend_request_policy` (`all` / `shared` / `nobody`, по умолчанию `shared`) и
  `users.dm_policy` живут в `internal/privacy`. `shared` — участники общих серверов: это тот же
  уровень знакомства, что у личек, поэтому он и безопасный дефолт.
- Блокировка из DM-3 отменяет заявку и удаляет дружбу: `privacy.Service` вызывает
  `friends.Service.CutOnBlock` через узкий интерфейс. Все проверки дружбы идут через privacy.
- `PolicyFriends` в личках теперь спрашивает `friends.Service.AreFriends`; nil — как раньше, никто
  не друг. Presence получает `FriendsOf` и публикует `presence.updated` в личный поток друзей.
- События: `friend.request.created`, `friend.request.removed`, `friend.added`, `friend.removed` —
  обеим сторонам через `PublishToUser`, payload в форме `FriendRequest` / `Friend` из OpenAPI.
- Лимиты: суточный бакет `ratelimit.NewDaily`, висящие заявки и число друзей — конфиг. При
  превышении — 429 с `Retry-After`, для друзей — 409.
- Общие данные пары — `GET /api/v1/users/{userId}/mutual`: серверы, где состоят оба, и друзья,
  которые есть у обоих. Это пересечение, не объединение. Эндпоинт живёт в `internal/profile`,
  потому что правило видимости уже там; серверы приходят через `servers.MutualServers`, друзья —
  через `friends.FriendsOf`, а профили общих друзей грузятся одним batch, без запроса на человека.
  Иконки серверов — подписанные ссылки, роль — роль вызывающего. Блок → 404, как чужой профиль;
  вопрос о себе → 400.

## Что видно кому (SCRUM-102)

Правило знакомства одно на все чужие данные: общий сервер, общая беседа или дружба. За его
пределами ответ — 404, как у несуществующего аккаунта, чтобы нельзя было перебирать id.

- Онлайн-статус — друзьям и участникам общих серверов; «Невидимка» превращается в `offline`
  (детали и тесты — в разделе «Онлайн-статус»).
- Профиль — только «знакомым». Свой профиль виден всегда.
- Общие списки — только тому, кто видит профиль. Блок перекрывает знакомство и тоже даёт 404,
  а вопрос о себе — 400: у пары должны быть две разные стороны.

## Профиль и онбординг (SCRUM-103, SCRUM-108)

`internal/profile` владеет профильными колонками `users`: имя, био, акцент, аватар, статус и
`profile_onboarded_at`. Публичный профиль — `UserProfile`; собственный — `SelfProfile`, который
добавляет `email` и `profileOnboardedAt`. В публичном профиле флага онбординга нет и быть не должно.

- Одноразовый шаг «Заполните профиль» отмечается только `POST /api/v1/users/me/onboarding` —
  и по «Сохранить», и по «Пропустить». Тела нет, ответ 204, вызов идемпотентен: первый timestamp
  сохраняется, повтор ничего не меняет. Гость получает 403: шаг начинается после регистрации или
  после ClaimGuest, который делает аккаунт обычным.
- Клиент показывает шаг, только пока `profileOnboardedAt` в `GET /auth/me` равен null; так же его
  видят другие устройства. Не заводи второй флаг, второй эндпоинт и не отмечай шаг через
  `PATCH /users/me/profile`.

## Роли и права (ROLE-1…3)

`internal/perms` — чистый расчёт без БД: база = @everyone ∪ роли участника, `administrator` → всё; в канале
сначала переопределения @everyone (`deny`, потом `allow`), затем объединённые переопределения ролей.
Владелец — всё. Таблицы `server_roles`, `server_member_roles`, `channel_role_overrides` принадлежат
`internal/servers` (роли) и `internal/channels` (переопределения).

- Биты прав (`perms.Set`) — это сохранённые данные: новые только добавляются в конец, старые не
  перенумеровываются. Канальные права — `perms.ChannelScoped`; остальные в переопределении — 400.
- Иерархия: менять роль, выдавать её и действовать над участником можно только ниже своей высшей роли
  (`MayManageRole`, `Outranks`), выдавать — только права, которые есть у самого (`MayGrant`). Владельца не
  трогает никто. Порядок ролей в БД — `DEFERRABLE` уникальный индекс (миграция 00021), сдвиг идёт одной
  транзакцией.
- Совместимость: `role` (`admin`/`member`) в `Membership` и `WorkspaceMember`, `memberPermissions` и
  `Channel.isReadOnly` выводятся из ролей для старых клиентов. Новое поведение на них не строй.
- События: `roles.changed` — всем участникам через `servers.Service.Announce`; выдача роли — `member.changed`;
  переопределение — `channel.changed`, а гейтвей заново решает, кому канал виден.
- Сквозная проверка с клиентом — `e2e/roles.spec.ts` в orbit-web (модератор, закрытый канал, иерархия).

## Push-уведомления (FEAT-4, SCRUM-126)

`internal/push` владеет таблицей `push_subscriptions` и отправкой Web Push (библиотека
`SherClockHolmes/webpush-go`: шифрование RFC 8291 и VAPID). Подробности и API — README,
«Push-уведомления».

- Отправляет только `messages.Service` через узкий `Notifier` (`notifyAway`): личка и группа — всем,
  кроме автора, тех, кто его заблокировал, и тех, кто выключил беседу; канал сервера — упомянутым и
  тем, кто выбрал «все сообщения» (уровни — `internal/notifysettings`), и только если они видят канал
  (`ChannelAccess.Get`). Не добавляй в `Notification` текст сообщения, вложения или что-то из секретных
  чатов: уведомление проходит через сторонний push-сервис и экран блокировки.
- `push.Service.Notify` не блокирует отправку сообщения: раунд идёт в горутине с собственным таймаутом,
  `Wait` ждёт его при остановке и в тестах. Пропускает тех, у кого открыта вкладка
  (`presence.Service.Connected`), и «Не беспокоить» (`DoNotDisturb`).
- Endpoint подписки принимается только `https` и только у известных push-сервисов (`pushHosts`) —
  сервер сам ходит по этому адресу, произвольный URL был бы SSRF. Новый сервис добавляй туда же.
- 404/410 от push-сервиса удаляют подписку, 2xx отмечает `last_success_at`, остальное — лог.
- Без `ORBIT_VAPID_*` push выключен: `GET /push/config` отвечает `enabled: false`, подписка — 503.
- Тесты: `internal/push` (адреса, кому уходит, мёртвые подписки, хендлеры, PostgreSQL),
  `internal/messages/notify_test.go` (получатели и отсутствие текста).

## Уровни уведомлений (FEAT-5, SCRUM-127)

`internal/notifysettings` владеет таблицей `notification_settings` (аккаунт, область, цель, уровень,
`muted_until`). Это единственное место, где считается «как громко» говорит сервер, канал или беседа:
push (`messages.notifyAway`) и клиент читают одно и то же правило.

- Канал наследует уровень сервера, затем идёт значение по умолчанию (`mentions` для канала сервера,
  `all` для беседы). `muted_until` в будущем на канале или сервере даёт `none`; из сроков побеждает
  самый поздний. Секретный канал не уведомляет никогда.
- Аудитория канала берётся батчем (`Levels` — один запрос на канал и его сервер), а не запросом на
  человека; получателей «все сообщения» не перебирай списком участников.
- API: `GET /notification-settings`, `PUT`/`DELETE /notification-settings/{scope}/{targetId}`.
  Цель проверяется на сервере; скрытый канал, чужой сервер, чужая беседа и секретный чат — 404.
  Лимит строк на аккаунт — `MaxPerUser`, сверх — 409.
- Изменение публикуется только аккаунту: `notification_settings.updated` через `PublishToUser`.
  Новое событие добавь и в `SERVER_EVENTS` web-теста `event-coverage.test.ts`.
